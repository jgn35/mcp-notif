- (constraint) Brief constraint: Self-hosted, Podman container, internet-exposed. Stack: Python async + FastMCP (server), Kotlin (Android app).
- (constraint) Brief constraint: LLM is the motor, not a feature — it decides when to notify, what to say, how to formulate. Android app is a read-only receptor.
- (constraint) Brief constraint: 3-field notification payload — title (notif title), short_message (notif body), detailed_message (shown on click).
- (constraint) Brief constraint: V1 read-only — no actions (mark done, snooze, reply), no notification history. Monouser, single device.
- (constraint) Brief constraint: Self-hosted, Podman container, internet-exposed. Stack: Python async + FastMCP (server), Kotlin (Android app).
- (version) MCP protocol spec 2026-07-28 — stateless at protocol level, Streamable HTTP transport recommended for remote servers. No session affinity needed.
- (version) FastMCP 4 (stable, GA) — supports MCP 2026-07-28 protocol, Python SDK v2.
- (version) Firebase Admin Python SDK 7.5.0 — requires Python 3.10+. Handles FCM HTTP v1 OAuth2 token acquisition automatically via service account credentials.
- (version) FCM HTTP v1 API — fully active, requires service account credentials (OAuth2). Legacy API deprecated. Cannot use bare API key for sending.
- (decision) Paradigm: Hexagonal (ports & adapters) for the MCP server. notify tool logic is the application core. MCP Streamable HTTP is the inbound adapter. FCM (firebase-admin SDK) is the outbound adapter. Android app is a thin receptor, not an architectural unit in V1.
- (decision) System topology: pipes-and-filters — LLM (cloud) -> MCP server (Podman) -> FCM (Google) -> Android app (device). Each stage transforms and forwards. No back-channel in V1.
- (decision) AD-1 notify tool input schema: three string fields — title, short_message, detailed_message. This is the contract the LLM calls against. Shared between MCP server and LLM.
- (decision) AD-2 FCM message contract: notification{title, body=short_message} + data{detailed_message}. MCP server sends this shape; Android app parses it. The only shared data contract between the two built units.
- (decision) AD-3 MCP server is stateless — no session state, no notification history, no database. Aligns with MCP 2026-07-28 stateless protocol and V1 no-history constraint.
- (decision) AD-4 Auth on the MCP server: static bearer token [ASSUMPTION]. Server is internet-exposed; monouser V1 needs minimum protection. Token passed in Authorization header. Exact rotation/TLS termination deferred.
- (decision) AD-5 Dependency direction: LLM -> MCP server -> FCM -> Android app. Strictly one-way in V1. Android app depends on FCM inbound only; no calls back to MCP server. No circular dependencies.
- (decision) AD-6 State ownership: LLM owns scheduling+formulation. MCP server owns nothing persistent (stateless). FCM owns delivery+device registration. Android owns transient display only.
- (decision) AD-7 Config management: env vars for MCP server (FCM_SERVICE_ACCOUNT_PATH, MCP_AUTH_TOKEN, FCM_DEVICE_TOKEN). Firebase google-services.json for Android. [ASSUMPTION: device token configured manually in V1, monouser single device].
- (decision) AD-8 Error handling: notify tool returns structured error to LLM if FCM push fails. LLM receives error and decides retry or skip. MCP server does not retry on its own in V1.
- (decision) AD-9 TLS termination: reverse proxy (Caddy) in front of Podman container handles HTTPS. MCP server listens on localhost only inside container. [ASSUMPTION: Caddy, could be Traefik/nginx].
- (decision) AD-10 Logging: structured JSON to stdout (container-friendly). No file-based logging, no log aggregation in V1. One log line per notify call with request id, result, latency.
- (assumption) [ASSUMPTION] Static bearer token auth is sufficient for V1 monouser. No mTLS, no OAuth2 server, no rate limiting in V1.
- (assumption) [ASSUMPTION] FCM device token configured manually via env var in V1. No automated device registration flow.
- (assumption) [ASSUMPTION] Caddy as reverse proxy for TLS. Could be swapped for Traefik/nginx — non-architectural choice.
- (assumption) [ASSUMPTION] No retry/dead-letter in V1. FCM is generally reliable; LLM handles retry logic.
- (assumption) [ASSUMPTION] Android app uses standard Firebase Messaging SDK. No custom push channel. Minimum Android version deferred to Android build.

- (direction) Deferred: Multi-user/multi-device, notification actions, notification history — out of V1 scope per brief.
